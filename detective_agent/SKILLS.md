# Detective Agent — Skills

This file documents what the agent in `detective_agent/detective_agent.py`
can and cannot do. It follows the same idea as an Anthropic SKILL.md: a
short, honest spec of the agent's actual capabilities, not an aspirational
description.

## What triggers this agent

It is invoked automatically by `orchestrator.py` whenever a live prediction
is later found to disagree with the real outcome (a confirmed false
positive or false negative) — never on a correct prediction, and never on
the real-time prediction path itself. It can also be run manually and
standalone via `detective_agent.py` against any known historical test case.

## Skill 1 — Evidence gathering (deterministic, no LLM)

**What it does:** for a given confirmed error, pulls four pieces of hard
evidence before any reasoning happens:
- the actual prediction and confidence that was made
- the true outcome
- the top SHAP-driving features behind that specific prediction
- a sensor-quality check (raw vs. `median_filter()`-cleaned reading, and
  whether an outlier spike was present in the simulated window)

**What it does NOT do:** speculate, infer, or invent evidence. Every field
comes from a direct function call against the trained model or the actual
reading — same code used elsewhere in the project (`median_filter.py`,
the SHAP explainer from `pipeline.py`'s approach).

**Reliability:** high — this is plain code, fully deterministic, same
output every time for the same input.

## Skill 2 — Root-cause investigation (LLM reasoning)

**What it does:** given the gathered evidence, an LLM (Claude or Groq,
auto-detected from environment variables) reasons about the most likely
cause of the error — e.g. "the dominant SHAP feature also had the largest
raw-vs-filtered noise gap, suggesting noise contributed to this error."

**What it does NOT do:** access any data outside what `node_gather_evidence`
already collected. It cannot look anything up, cannot call external tools,
and is explicitly instructed not to speculate beyond the provided evidence.

**Reliability:** medium — LLM output is not deterministic (rerunning can
give a differently-worded conclusion), and has not been independently
validated for accuracy on this project's specific failure patterns. Treat
its output as a reasoned hypothesis for a human to check, not a proven
diagnosis.

**Fallback:** if no API key is set, a rule-based deterministic summary
runs instead (see `node_investigate`'s `else` branch), clearly labeled as
such in its own output.

## Skill 3 — Report writing (LLM formatting)

**What it does:** turns the investigation notes into a short, plain-
language case file — a one-line verdict, supporting evidence bullets, and
a recommended next action — written for a non-technical reviewer.

**What it does NOT do:** make any decision. Every report ends in a
recommendation for a *human* to act on (e.g. "confirm sensor data quality
before deciding whether retraining is warranted") — never an automatic
action.

**Reliability:** medium-high — formatting/summarization is a task LLMs are
reliably good at; the risk here is inheriting any inaccuracy from Skill 2,
not introducing new ones.

## Explicit non-skills — things this agent cannot and must not do

- **Cannot retrain the model.** No node in this graph touches
  `pipeline.py`'s training logic.
- **Cannot change the deployed model, threshold, or filter.** Read-only
  with respect to the live system.
- **Cannot act on the grid.** No connection to any actuator; see the main
  README's "what this project isn't" section.
- **Cannot investigate a correct prediction.** By design, only runs on
  confirmed mismatches.
- **Cannot fabricate evidence.** Every evidence field is sourced from a
  deterministic function call, never generated by the LLM.

## Known limitations, honestly stated

- The sensor-quality check (`check_sensor_quality`) simulates noise for
  demonstration — it is not reading a real sensor log, because this
  project is not connected to a real grid.
- The LLM's reasoning quality (Skill 2) has not been benchmarked or
  validated — no ground-truth "correct root cause" labels exist to score
  it against. Its usefulness has been demonstrated structurally (the graph
  runs, evidence flows correctly — see the orchestrator.py fix that
  corrected a real evidence-mismatch bug), not empirically validated for
  diagnostic accuracy.
- `orchestrator.py` simulates the "ground truth becomes known later" step
  using test-set labels that are already known in advance. A real
  deployment would need an actual delayed feedback channel from live grid
  monitoring, which does not exist in this project.
